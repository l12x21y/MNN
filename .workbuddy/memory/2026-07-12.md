
## 眼动记录视频实验改造 (2026-07-12 晚)
- 用户目标: 用电脑摄像头做眼动追踪, 被试看视频时同步记录"电脑时间 + 注视点屏幕坐标"。
- 结论: 原框架已具备 webcam 眼动追踪与每帧坐标输出; 原 demo.py 只是空白 pygame 循环, 不会放视频。
- 改造1 GazeFollower.py:
  - `_gaze_info_2_string` 新增可读列 `datetime`(由 `time.time_ns()` 纳秒时间戳转本地电脑时间, 格式 %Y-%m-%d %H:%M:%S.%f)。
  - 新增 `_coord_pair` 安全取值, 处理 face/gaze 失败时坐标为 None 导致崩溃的问题(原代码直接取 [0] 会 TypeError)。
  - CSV 表头同步改为 14 列: timestamp,datetime,raw_x,raw_y,calibrated_x,calibrated_y,filtered_x,filtered_y,left_openness,right_openness,tracking_status,status,event,trigger。
- 改造2 demo.py: 重写为"校准 -> 全屏放视频 -> 实时叠加绿色注视点 -> ESC 保存"。
  - 支持 `python demo.py [视频路径]`; 无视频参数则黑屏记录。
  - 视频用 cv2.VideoCapture 读取, pygame.surfarray 全屏渲染(transpose (h,w,3)->(w,h,3))。
  - 视频开始帧发送 trigger=1 供 CSV 同步标记。
- 关键约束: SAMPLING 硬依赖校准(未校准会抛异常), 故流程必须先 calibrate 再 start_sampling。
- 待办/局限: 视频无音频(如需声音可另开播放器或用其他方案); 性能上摄像头线程(30fps 推理)与视频渲染同机, 低端机可能掉帧。

## demo.py 五次改造 (22:38) — 视频卡顿优化 + 两版热力图
- 用户反馈: 视频在工具里播放"非常明显卡顿", 实验不能出现; 并要求热力图做"保留视频画面"和"不保留视频画面"两版。
- 卡顿根因(三处叠加):
  1. 每帧 `frame.transpose(1,0,2)+make_surface` 做转置并重建 6MB surface, 开销大。
  2. 每 5 秒 `emit_window()` 同步跑 matplotlib(100~500ms) 阻塞主循环 -> 周期性明显顿挫(主因)。
  3. 解码缓冲未控, 偶尔读到滞后帧。
- 优化:
  - 显示改为 `pygame.image.frombuffer(frame_rgb.tobytes(),(W,H),"RGB")`: 不转置、不每帧重建 surface, 直接封装 RGB 行主序帧(与 cv2 输出天然吻合); 仅尺寸不一致时 cv2.resize。
  - 热力图渲染搬到后台线程(`threading.Thread` + `_render_lock` 串行化 matplotlib 全局状态), 主循环不再被阻塞; emit_window 仅做轻量记账(编号/清点), 实际 PNG 在子线程出; 结尾统一 `join` 所有渲染线程防丢图。
  - `cap.set(cv2.CAP_PROP_BUFFERSIZE,1)` 降延迟; `clock.tick(fps)` 按原始帧率匀速播放(fps 取自 CAP_PROP_FPS, 兜底 30)。
- 两版热力图: emit_window 现在一次窗口同时渲染 `gaze_时间/n.png`(干净版, bg=None) 与 `gaze_时间/n_video.png`(带视频画面版, bg=last_frame BGR 副本) 两组。make_heatmap.py 无需改动(render_heatmap 已支持两种 bg)。
- 验证: py_compile 通过; 合成数据实测两版均出图(_tmp_clean.png 83KB / _tmp_video.png 76KB, 尺寸正确)。

## 八次改造 (23:42) — 真正启用 GPU (Vulkan backend=4)
- 实测环境(本机 .venv, Windows, MNN wheel 版本未知): 跑 `test_mnn_gpu.py` 结果:
  - backend=2 OpenCL: **伪GPU**——创建不报错但 MNN 静默回退 CPU(日志 "Can't Find type=2")。
  - backend=4 Vulkan: **真 GPU**——真正在 GPU 上推理成功。
  - backend=5 CUDA: 伪GPU(静默回退)。
  - backend=0 CPU: 可用(改造前实际一直走这里)。
- 根因: 第6次改造设的候选 `[2,0]` 只试 OpenCL, 而本机 OpenCL 不可用 -> fell_back 被探测逻辑跳过 -> 落到 CPU, **从未尝试 Vulkan**, 故长期误以为只能用 CPU。
- 改动 (gazefollower/gaze_estimator/MGazeNetGazeEstimator.py): 默认候选改为 `[2,4,0]`(OpenCL -> Vulkan -> CPU); 文档注释同步更新。逻辑复用已有 probe_all(识别静默回退)+ load_module(进程内自检), 安全回退不变。
- 验证: 用 stub 掉父包 __init__ 的方式单独加载 mnn_probe, 复现候选逻辑 -> 实测选中 backend=4(Vulkan GPU), 不再回退 CPU。断言通过。
- 结论: **本机 MNN 现在默认自动用 GPU(Vulkan)**, 无需改环境变量。也可 `set GAZEFOLLOWER_MNN_BACKEND=4`(PowerShell: `$env:GAZEFOLLOWER_MNN_BACKEND=4`) 强制。
- 遗留: 人脸检测 BlazeFaceAlignment.py 仍硬编码 `backend=0`(CPU), 未享受 GPU。需要的话可同样套用 probe_all/load_module 改造 blaze_face.mnn(输入名 image/conf_threshold/max_detections/iou_threshold, 输出 selectedBoxes)。

## 十三次改造 (00:42) — 定位并消除"播放仍卡顿"的真正根因
- 用户复跑(视频已缩到 30s)仍报:"还是卡的"。说明移除可视化后仍有卡顿, 真瓶颈在播放循环本身 + 眼动推理线程抢资源。
- 真因有两条(已读代码确认):
  1. **播放循环每帧分配 ~6MB(卡顿主因)**: 原 `surf = pygame.image.frombuffer(frame_rgb.tobytes(), (W,H), "RGB")` 每帧都 `cvtColor` 拷贝 + `tobytes()`(6MB bytes 新分配) + 新建 surface; 30fps 下 ≈360MB/s 分配 → 周期性 GC 抖动 → 肉眼"卡顿/顿挫"。
  2. **眼动推理线程满负荷**: `gazefollower/camera/WebCamCamera.py` 的 `capture()` 循环对每帧 webcam 都调 `process_frame`(MediaPipe 人脸对齐占 CPU + MNN 注视推理占 GPU), **无速率限制、无 sleep**, 与视频解码(CPU)+ 显示 blit(GPU) 抢同一份 CPU/GPU 资源。
- 修复(已做, demo.py, 安全无副作用): 消灭每帧分配。
  - 循环前**只建一次**: `rgb_buf = np.empty((H,W,3), uint8)` + `surf = pygame.image.frombuffer(rgb_buf,(W,H),"RGB")`(经无头测试确认 frombuffer 与 ndarray **共享内存**, 改 buf 即改 surf 像素)。
  - 循环内改为**原地写缓冲**: `rgb_buf[:] = frame[:,:,::-1]`(BGR->RGB 原地翻转通道, 零分配; 仅当视频分辨率≠屏分辨率时才 `cv2.resize` 产生一次 small 分配)。然后 `screen.blit(surf, (0,0))` 显示即刚写入的帧。
  - 已在无头(dummy SDL)环境验证 frombuffer 共享内存 + blit_array(transpose) 两种零分配方案均可用, 选了更简洁的 frombuffer 共享方案。
  - 验证: py_compile 通过; grep 确认播放段已无 `frame_rgb`/`tobytes`/`cvtColor(frame,...,BGR2RGB)` 残留。
- **尚未做(需用户确认, 有取舍)**: 第 2 条的眼动推理线程满负荷。彻底消除需给 `WebCamCamera.capture()` 限速(例如每 2 帧才做推理 / 降到 ~15fps), 这会**降低 CSV 采样密度**(对热力图无影响, 但逐帧注视轨迹会由 30Hz 变 15Hz)。因涉及共享库行为且影响采样率, 未擅自改; 若用户复测仍有卡顿, 再按此方案限速。
